# Immersive Brewing 1.1.0 implementation report

Status: **core implementation and automated validation complete; human release gates pending**. This report maps the current implementation to
`Immersive_Brewing_1.1.0_Recommendations.md`. It is not a release announcement and does not turn automated checks into
human-play evidence.

## Release boundary and decisions

The five direction choices in the recommendations are explicit in the implementation:

1. **Registered brewing remains authoritative.** Infusion data describes a transformation; the live adapter must
   reproduce it. Catalog results, saved keys and quick finishing are re-resolved against current server recipes.
2. **Raw reagents remain usable.** A raw preparable reagent contributes extraction 50. Mortar preparation is the route
   above the raw ceiling toward Masterwork, not an entry fee for the first or an ordinary batch.
3. **Accessibility is not automation.** Hold/toggle, reduced-input, narration, palettes and server-approved timing/band
   assistance keep the full scoring range. Unattended Kettle production is not implemented.
4. **The quality model remains bounded.** The existing extraction/control formula, grade bands, eligible-duration curve
   and inheritance policy remain authoritative. Journal, rack, staging and finishing add no score or reward milestone.
5. **The target remains Minecraft 1.20.1, Forge 47.4.23 and Java 17.** Other loaders and simultaneous ports are deferred.

Additional conservative choices resolve ambiguities in the recommendations:

- Catalog traversal is shortest-first and bounded. An incomplete, budget-limited or omitted-alternative result is not
  called exhaustive or unsupported; contextual handlers are queried from the open tray rather than guessed enumerable.
  Rejected candidates count against discovery work; inventory filtering has a separate 32-route slice. Selected keys
  replay only their referenced sources. The carrier selector cycles through inventory slots and returns to none.
- A saved plan key is a hint, never authority. Repeat, pin, practice and final selection re-resolve on the server.
- Batch staging can use bottles from one explicitly selected carrier. Reagents, fuel and tools come only from the open
  Kettle and ordinary player inventory; nearby unopened inventories are never searched.
- Quick finishing is limited to live, proven potion→splash or splash→lingering vanilla-winner conversions with
  equivalent canonical contents. A `container` role label alone is insufficient.
- Finishing is a dedicated **Finish batch** action alongside the route preview, sharing its exact-cost and inventory
  validation, rather than a separate duplicate catalog tab. Its default is seven seconds and the server can disable it.
- The first rack is one six-slot flagship block. Additional material/apparatus variants and direct carrier drinking are
  deferred instead of broadening the validation surface.
- Guide data version 2, job-ledger schema 2 and carrier/rack preference payloads migrate known old data conservatively;
  unknown newer or unsafe job data is preserved rather than downgraded or partially interpreted.

## UI regression follow-up (2026-10-28)

The kettle heat-trend label started at `py + 33` while the progress bar occupied `py + 35..39`. Its nine-pixel text
line crossed the bar, and its fixed 54-pixel width truncated longer translations. The initial/resume countdown was
also floating over the apparatus without a reserved background. Both now use the existing dark header status row:
264 text pixels at a 320x240 GUI, with five clear pixels between the text line and the progress bar. The phase/time
and optional numeric score remain visible beside the heat trend during play; the countdown occupies that row while
waiting to start or resume. Colors continue to use the existing accessibility palettes. Guided-lesson instructions
also overlapped the header at y=24; they now use the reserved, two-line cue strip below the vessel.

All 39 rack/carrier keys and every other key in the four non-Chinese production locales were already free of CJK.
The source offender was a hardcoded Chinese sample shelf label in the rack/carrier smoke-test workflow. Sample
labels now come from five test-only locale files, with Simplified Chinese confined to `zh_cn.json`. The visual
matrix refreshes the rack label after language changes and waits for the newly localized carrier stack to synchronize
before opening its screen. It checks the actual editable name field, not just the inventory metadata. Player-authored
labels remain intact. No production translations needed replacement and no test translations enter the release jar.
